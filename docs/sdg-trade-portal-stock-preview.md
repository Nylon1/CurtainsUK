# SDG trade-portal stock: Preview integration

The authenticated SDG trade portal's product listing and stock-detail modal show current per-SKU quantities. On 18 September 2026, the portal loaded `https://supplier.sandersondesigngroup.com/EdiNextCore/api/Product/detail` for those figures. Its own client posts exact `productCode` values in batches of up to 130 with `stock: true`; it renders `stockInformation.primaryStock` using `productStockUnit`. The Document Browser's latest `All Product Data` export was dated 14 September, so that export does not establish current coverage.

`lib/supplier-sync/adapters/sanderson-design-group.ts` reads only this authenticated detail service, in sequential batches of 100. It accepts an exact Fabric Master SKU/brand manifest, checks returned SKU identity and metre units, and records zero only when the supplier explicitly returns numeric zero. Missing responses, missing quantities, duplicate SKUs and non-metre units become exceptions. It does not import price, future stock, samples or lifecycle from the stock response. `checked_at` is the retrieval time of the authenticated response; the service does not expose a separate supplier-update timestamp in the portal UI. The existing 72-hour stock validity remains unchanged.

The operator script `scripts/curtainsuk-preview-sdg-portal-stock.ts` accepts a private JSON manifest of `{ "supplierSku": "...", "brandId": "..." }` records and a short-lived `SDG_PORTAL_BEARER_TOKEN` supplied in the process environment. It writes the raw read result and exceptions under ignored `artifacts/sdg-portal-private/`. The token is never written or printed. It stops on authentication failure or supplier throttling. It does not initiate supplier orders or Shopify writes.

`--apply-preview` additionally requires a dedicated Supabase Preview branch URL, its matching `CURTAINSUK_SDG_PREVIEW_SUPABASE_REF`, `CURTAINSUK_DEPLOYMENT_STAGE=preview`, and that branch's `SUPABASE_SECRET_KEY`. The Production project ref `hqysjumypgeapgmqkcrx` is explicitly denied. Valid observations enter the **existing supplier snapshot validation/history pipeline as shadow evidence**; the script does not auto-approve them or materialise a customer stock state. Existing governed approval and materialisation must run in Preview after the exception/coverage report is reviewed.

The prior Preview database integration remains separate from the read-only proof below. Do not point the older operator script at Production or promote supplier stock on the basis of the old export. The 72-hour fail-closed state remains authoritative until observations pass the governed import/materialisation path.

## Authenticated read-only proof

`scripts/curtainsuk-sdg-portal-stock-proof.ts` is a separate **read-only** operator proof. Run it from an interactive terminal with `npx tsx scripts/curtainsuk-sdg-portal-stock-proof.ts`. It prompts for the authorised trade-account email and hides password entry; neither is supplied on the command line, saved to disk, or printed. It establishes its own in-memory first-party session through the portal's observed `customer/login` endpoint, obtains the Product/detail bearer through the observed `mertex/refreshToken` endpoint, and refreshes before expiry. It never imports browser cookies or persists a bearer as a Production secret. If the portal requires a different login challenge or rejects independent session refresh, it stops with a safe error code rather than bypassing the challenge.

The proof uses the ignored 8,636-SKU exact manifest, runs 1 → 10 → 100 SKUs, explicitly tests a second first-party token refresh, then—only if those stages are stable—runs sequential 100-SKU batches over the full manifest. `--stages-only` stops before the full run. Each Product/detail response is checked against its requested exact SKU and metre unit. The private report preserves available-now, offsite and future quantities, supplier descriptions, future due dates, batch/piece information, exceptions, authentication timing and per-batch latency/retries. Only `primaryStock` can become the existing normalized current-stock observation; future and offsite stock are never treated as available now. An unsuccessful request produces no new stock observation.

Reports are written only to ignored `artifacts/sdg-portal-private/` and are marked incomplete until the entire requested run finishes. `--start-at=CHECKPOINT` can continue at a proven 100-SKU checkpoint, writing a new report while preserving the earlier one. A batch-level HTTP 404 is recorded as unresolved for every SKU in that batch; it never becomes zero stock. This script has no Supabase or Shopify client and makes no database, order, or Production writes. The token's reported lifetime is read from the supplier response; the trade session's maximum lifetime cannot be claimed unless a natural expiry is observed. The account owner confirmed that the password exposed in an earlier screenshot was changed through the normal SDG account flow before this proof ran. No replacement credential was saved.

A read-only query of Fabric Master found 8,636 non-discontinued SDG colourways, all with distinct supplier SKUs, from 9,680 SDG records total. Their exact SKU/brand manifest is saved locally at `artifacts/sdg-portal-private/current-sdg-identities-2026-09-18.json` and ignored by Git.

### 18 September 2026 dry-run result

The authenticated read-only run covered all 8,636 manifest SKUs across 87 sequential batch positions, in two checkpointed segments. The first 79 completed batches resolved 7,860 SKUs and found 40 absent from a partial portal response. The next batch returned HTTP 404; the continuation preserved the first report and marked 404 batches unresolved while completing the remaining eight positions. There were also three staged 1/10/100-SKU requests and two diagnostic attempts of the failed 404 batch, for **92 actual Product/detail HTTP requests**. Combined result: **7,861 exact SKU/metre observations** and **775 unresolved Zoffany SKUs** (139 absent from response lists, 636 in 404 batches). All other five SDG brands had complete exact-SKU coverage. No 404 or missing response was interpreted as zero stock.

Of the 7,861 observations, 5,355 showed at least 30 metres available now, 1,177 showed positive stock below 30 metres, and 1,329 showed explicit numeric zero. Offsite quantity was positive for none; 1,191 showed future stock with a due date. Future stock does not count as available now. There were zero retries and zero rate-limited responses; measured request time totalled about 231 seconds. The first-party token response reported about 58 minutes of lifetime, and explicit refresh succeeded in both authenticated sessions. This proves refresh works while the session is active, not its maximum lifetime or unattended daily-login reliability.

The raw split reports and combined aggregate summary, including report SHA-256 hashes, are retained under ignored `artifacts/sdg-portal-private/`. No Supabase branch or Production record was written. The 775 Zoffany exceptions need supplier/account-specific clarification or a separately proven source before they can receive current observations. Do not activate a daily scheduler or materialise these dry-run observations from this evidence alone.

The first dry-run reports retained per-SKU quantities and run timing but not the normalized per-SKU `checked_at` snapshots. The proof script now retains those snapshots for future fresh reads. Do not reconstruct individual observation timestamps from the first report's start/end times or re-date those observations for import. Any database materialisation must use a fresh supplier read with its own exact observation timestamps.

The bounded 404 isolation added after the first run budgets at most 15 Product/detail calls for a failed 100-SKU batch, apart from any separately bounded network/rate-limit/server retries. It can recover valid neighbours when one identity poisons a batch, while leaving unresolved SKUs unknown. In a separate fresh authorised session, one non-Zoffany control resolved, but all 100 legacy Zoffany SKUs in the isolated test remained 404-affected; the two historically mapped current `ZOF` portal IDs also returned singleton 404. This supports a Zoffany Product/detail access/service limitation, not an isolated bad SKU. The 775 records are all `UNKNOWN` lifecycle from the 24 February authorised XLSX catalogue. Neither current lifecycle nor a reliable stock-code mapping for them can be inferred from this test.

The 139 exact SKUs absent from successful partial responses are retained in ignored `artifacts/sdg-portal-private/zoffany-identity-exceptions-2026-09-18.json`. Each is linked to its existing Fabric Master brand and February source, with current identity/lifecycle explicitly `UNVERIFIED`. They are a supplier reconciliation queue, not discontinued or zero-stock classifications. The two previously evidenced `ZINF` → `ZOF` card mappings remain individually valid identity evidence, but their current stock is still unconfirmed because Product/detail returned 404 for the `ZOF` codes too.

An isolated Supabase development branch was requested with the owner's confirmed hourly cost, but Supabase rejected creation because this project is not on a plan that supports branching. No database test or write was attempted on the Production project. The local machine has neither Supabase CLI nor Docker/Postgres available for an equivalent isolated database rehearsal. Development-branch materialisation remains unproven and is required before a Production stock import.

The existing supplier snapshot payload and `daily_stock_snapshots.aggregate_metres` preserve the actual numeric metre quantity and source observation time. Read-only inspection of the current database confirmed both. Its customer commercial-evidence function still applies a fixed `>=30` threshold; this dry-run hardening does not change that Production rule. A requirement-specific quantity decision for Curtain Builder remains a separate governed change before Production activation of this connector.
